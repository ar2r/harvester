# Начало работы

Установка, настройка и первый запуск LedgerFox.

## Требования

- **Go** не ниже 1.24 — для сборки из исходников (для релизных архивов не нужен);
- SQLite уже встроена в драйвер, отдельный сервер БД не требуется.

## Сборка

```bash
make build
```

Бинарники собираются в `bin/` (`app` — приложение, `mocklkdr` — мок ФНС для тестов).

## Как устроено приложение

Приложение собирает чеки из внешних систем **задачами** (jobs) и запускает их
**триггерами**. Сейчас существует одна задача и один триггер:

- **`lkdr`** — чеки и фискальные данные из ЛК ФНС «Мои чеки онлайн»: первая
  синхронизация тянет последние 12 месяцев (или с даты `firstSyncFrom`
  в конфиге — например, `"firstSyncFrom": "2020-01-01"`, или за
  `firstSyncMonths` последних месяцев — настройка конкретного пользователя),
  дальше — только новые чеки; после
  загрузки чеков дозагружаются их фискальные детали (состав покупок);
- **`stdin`** — ручной запуск: интерактивная командная строка или однократный
  режим (см. ниже). SMS-коды для авторизации запрашиваются прямо в терминале.

Одна и та же задача для одного пользователя не выполняется параллельно;
разные пользователи и задачи — могут. Ошибка любого включённого модуля на
старте — паника (fail-fast, частичного старта нет). Встроенного планировщика
нет: периодичность — внешний cron с однократным режимом (предварительно
авторизуйтесь интерактивно, SMS в фоне не спросить).

## Конфигурация

Создайте `config.json` в корне (полный справочник — [Конфигурация](configuration.md)):

```json
{
  "stdin": { "enabled": true },
  "captcha": { "rucaptchaKey": "<API-ключ RuCaptcha>" },
  "lkdr": {
    "enabled": true,
    "database": { "dsn": "lkdr.db" },
    "users": {
      "a": [{ "phone": "79001234567" }]
    }
  }
}
```

`config.json` содержит личные данные — он исключён из Git (`.gitignore`).

## Первый запуск

```bash
make parse
```

Выполняется парсинг чеков **всех пользователей из конфигурации по очереди**:
чеки пользователя загружаются до конца, затем приложение переходит
к следующему, а после последнего — завершается. Отладочный вариант
с DEBUG-логами и одним пользователем: `make run RUN_USER=a`.
Прямой запуск бинарником:

```bash
./bin/app --config.file=config.json --stdin.user=all
```

Приложение запросит код из СМС, авторизуется и начнёт выгрузку. Токены
сохраняются в базе — повторная авторизация не потребуется. Код возврата:
`0` — успех, `1` — ошибка задачи. Полезные флаги: `--debug` (уровень DEBUG),
`--json` (весь вывод построчным JSON).

Первая авторизация требует решения капчи — приложение делает это только
автоматически, через API RuCaptcha, поэтому ключ нужен минимум на первую
авторизацию. Без ключа задача завершится ошибкой
`authorizer is required, but not set`. После авторизации токены хранятся в
базе и ключ больше не участвует; продвинутый вариант без ключа — единожды
перенести токены из авторизованной сессии браузера в таблицу `tokens`
базы SQLite, дальше приложение обновляет их само.

## Отчёты

По локальной базе `lkdr.db` строится текстовый отчёт по покупкам:

```bash
make lkdr-report
```

Полный гайд по отчёту — [Отчёт по покупкам LKDR](lkdr-report.md).

## Частые проблемы

- **Капча при авторизации** — приложение решает капчу только автоматически,
  через API-ключ RuCaptcha в секции `captcha`; без ключа первая авторизация
  падает с ошибкой `authorizer is required, but not set`. Обходной путь —
  единожды перенести токены из авторизованной сессии браузера в таблицу
  `tokens` базы SQLite.
- **SMS-код в фоновом запуске** — интерактива нет; сначала авторизуйтесь
  через `stdin`, затем cron-запуски заработают.
- **`receipt.fiscal.data.unavailable`** — загрузчик деталей допускает до 5
  таких пропусков за запуск, следующий останавливает его; повторный запуск
  продолжит с места остановки.
- **Неофициальное API ФНС** — изменения на стороне сервиса могут ломать сбор.
